Three bugs found reviewing gossms and gosmo, all in the whole-database
scripting that shipped in gossms `3e44d72` / gosmo `af97e81`
(`ScriptDatabaseObjectList`, `scripting.DatabaseObjects`, Generate Scripts).
None is in `docs/open-threads.md` or `~/go/gosmo/OPEN-THREADS.md`. Each was

Delete this file once its items are done or moved to open-threads.

IDs are local to this plan (`G` prefix).

## G1: dotted names collide, so one object is scripted twice and another never (gosmo)

**Status: done 2026-11-06** (gosmo, uncommitted): bracket-quoted `objectKey`,
duplicate-key error in `orderObjects`, unit tests, live fixture plus a
QUOTENAMEd, count-based catalog comparison. Passed live on win10cli.

**Symptom.** A database with `[a.b].[c]` and `[a].[b.c]` (both legal) gives a
script that creates `[a.b].[c]` twice and never creates `[a].[b.c]`. A replay
succeeds, because the second CREATE is behind `IF OBJECT_ID(...) IS NULL`, so
nothing warns that the table is missing. The script header and the
record's object count don't mention it either.

**Cause.** `objectKey` (`~/go/gosmo/scripter_database_objects.go`) builds
`prefix + ":" + schema + "." + name`, and the result isn't injective. Both
objects get the key `o:a.b.c`. In `ScriptDatabaseObjectList`, `items[n.key]`
keeps only the last generator, while `nodes` holds both entries. Each node then
emits the same `items` entry. `historyTables` and `dependencyOrderEdges` use the
same key, so dependency edges can also attach to the wrong object.

**Fix.**
1. Make the key injective by quoting each part:
   `string(prefix) + ":" + QualifiedName(schema, name)`. Bracket quoting doubles
   `]`, so no two (schema, name) pairs give the same string. This changes no
   exported API.
2. Also catch duplicate keys defensively. `orderObjects` should refuse a
   duplicate node key with an internal error. Silently ignoring it is what hid
   this bug.

**Tests.**
- Unit test in `scripter_database_objects_order_test.go`: `objectKey` distinct
  for `("a.b","c")` vs `("a","b.c")`. `orderObjects` refuses a duplicate key.
- Live: add `[a.b].[c]` and `[a].[b.c]` to the fixture in
  `live_script_database_objects_test.go`. Replay the script, then compare the
  table list of the source and replayed databases. The existing test only
  checks that the replay ran without error, and this bug doesn't raise one.

## G2: ledger tables make the script fail on replay (gosmo)

**Status: done 2026-11-06** (gosmo, uncommitted): `createdByParent` (gated
through `colSince`/`bitSince`, golden file `created_by_parent.sql`, three
inventory entries) skips history tables and ledger views and notes a dropped
ledger view. The replay fixture gained an updatable, an append-only and a
dropped ledger table, and requires no notes but the dropped table's and
its view's. Passed live on 17 (mutation-checked: Msg 2714 is back without
the view filter) and 13 (replay, gated columns, `TestLiveVersionSweep`).

**Symptom.** For an updatable ledger table, `CREATE TABLE ... WITH
(SYSTEM_VERSIONING = ON, LEDGER = ON)`:
- the replay fails with **Msg 2714 "There is already an object named
  'L_Ledger'"**. The ledger view is listed by `Views` (`is_ms_shipped = 0`) and
  scripted as a bare `CREATE VIEW` after the table, but the table's own
  `LEDGER = ON (LEDGER_VIEW = ...)` has already created it.
- the history table `MSSQL_LedgerHistoryFor_<id>` is scripted as a
  `-- not scripted: ... ledger history table` comment. It shows up as a note in
  the gossms status bar and in the CLI `NOTES:` field, as if something were
  lost. Its parent table creates it, as with temporal history tables.

**Cause.** `historyTables` selects `temporal_type = 1` only. An updatable
ledger table's history table is `temporal_type = 0, ledger_type = 1`
(confirmed live). Nothing excludes `sys.tables.ledger_view_id`.

**Fix** (`~/go/gosmo/scripter_database_objects.go`):
1. Rename `historyTables` to `createdByParent` and extend its query to
   everything another table's CREATE creates:
   `temporal_type = 1 OR ledger_type = 1` for tables, and
   `ledger_view_id` for views. Use `colSince(major, SQLServer2022, ...)`
   for 2022+ columns (`ledger_type`, `ledger_view_id`), or skip the ledger
   part below 16.
2. Filter `views` against that set, as `tables` already is.
3. Dropped ledger tables (`is_dropped_ledger_table`) keep their refusal note.
   Their dropped ledger views (`sys.views.is_dropped_ledger_view`, 2022+)
   should also become a note, not a CREATE VIEW over a table that doesn't
   exist.
4. Update the `ScriptDatabaseObjectList` doc comment: "a system-versioned
   or ledger table's history table and ledger view (its parent creates
   them)".

**Tests.**
- Live (17): add an updatable and an append-only ledger table to the replay
  fixture. The replay must succeed, with no notes, and the replayed database
  must have the same ledger view name.
- Run `TestLiveVersionSweep` on 13 (`win10cli\SQL2016`), since the query now
  names 2022 columns.
- Version-gate golden test, if `createdByParent` goes through
  `colSince`/`bitSince`.

## G3: Generate Scripts times out after 30 s and can't be cancelled (gossms, with an optional gosmo change)

**Status: done 2026-11-06** (both repos, uncommitted). gosmo: every list is
read before the first object is scripted (`scriptQueue`), so
`ObjectScriptOptions.Progress` gets (0, total) then one call per object;
foreign keys render from the table prefetch (`tableForeignKeys`,
`scriptTableForeignKey`). The live fixture's new FK extended property found
a pre-existing bug, fixed: under `DeferForeignKeys` the table script carried
its deferred FK's property, and the replay failed Msg 15135. Live replay test
asserts progress and each FK entry == `ScriptForeignKey`; passed on 17 and 13
(plus `TestLiveVersionSweep` on 13). gossms: a Background Task with
whole-percent progress and Cancel, no deadline; the count excludes the
principals/permissions blocks and noted entries (`countScripted`). The
"Scripted N objects" message is now set after the query window connects
(`openQueryWithTextThen`); before, the connect's own status replaced it.
Driven live: 12,300 objects in 40 s, progress shown, Cancel → "cancelled"
with no window, count = CLI `objects`.

**Symptom.** Generate Scripts runs through `App.generateScript`
(`internal/tui/scripting.go`), and that wraps the whole database in
`context.WithTimeout(..., childFetchTimeout)`, which is 30 s. Measured live:
~25 ms per module on LAN (407 objects 10.4 s; adding 300 tables plus 300 FKs
added only ~2 s, because the table prefetch works). So a database with roughly
1,200+ procedures, views and functions fails on LAN with "Script error: context
deadline exceeded", and over a WAN or to Azure it fails far sooner. Everything
read up to then is discarded. Until then there is no progress and no Cancel,
only "Scripting <db>..." in the status bar. The CLI path (`script db --objects`)
has no such cap.

Related, same code: the status message "Scripted N objects" counts
`len(r.Objects)`. With Include permissions on, that includes the
`ScriptedPrincipals`/`ScriptedPermissions` pseudo-entries (+2), and it also
counts comment-only entries that weren't scripted.

**Fix.**
1. gossms (`internal/tui/generate_scripts_dialog.go`): don't go through
   `generateScript`. Run under `App.startTask(sc.Server.Context(), "Generate
   Scripts: <db>")` (`internal/tui/tasks.go`) with no fixed timeout. Start the
   goroutine with `safegoRepair` → `markTaskDone`, and report through
   `postTaskDone`. This lists the run in Background Tasks with Cancel, and
   disconnecting cancels it (ARCHITECTURE.md § background work).
2. gosmo (breaking change allowed): add
   `ObjectScriptOptions.Progress func(done, total int)`, called from
   `ScriptDatabaseObjectList` after each emitted object (total is known once
   `orderObjects` returns, plus FKs and triggers). gossms forwards it to
   `postProgress`, throttled to whole-percent changes so it doesn't flood
   `postAndWake`.
3. gosmo: step 3 re-reads foreign keys per table (`t.ForeignKeys`), then per FK
   (`ScriptForeignKey` → `TableByName` + `ForeignKeys` again). Instead, render
   from `s.tables.fks` (the prefetch already has them) through the builder
   `ScriptForeignKey` uses. This removes 1 + 2×FK queries per table.
4. `scripting.DatabaseObjects`: count only entries whose `Kind` is a real
   object (not principals/permissions) and whose `Note` is empty. Report the
   noted ones separately, as it already does.

**Tests.**
- gosmo unit: `Progress` called monotonically, ending at `total == done`.
- gosmo live: FK script text unchanged after (3). The existing replay test
  covers this, plus a byte-compare of the FK section before and after.
- gossms: drive the built binary (`docs/testing.md`) against a throwaway
  database with ~1,500 generated procedures. The task appears in Tools ▸
  Background Tasks with progress, completes past 30 s, Cancel stops it
  ("cancelled" status, no query window), and the count matches the CLI
  `OBJECTS:` minus pseudo-entries.
