## Steps, in order

### F1 — gosmo: whole-database script creates a user mapped to a certificate or key it never creates

**Done 2026-11-18.** `buildDatabaseSecurityParts` comments out, under a
scope, a certificate- or key-mapped user and every statement naming it
(schema/role ownership, memberships, GRANT/DENY to or on it); the schema it
owned is created under dbo. The principals block now gets a scope too
(`queuePrincipalsAndPartitioning` passed nil). Unit test
`TestDatabaseSecurityPartsLeavesOutMappedUsers`; live
`TestLiveScriptDatabaseObjectsMappedUsers` replays clean on 13 and 17 (and
fails with the head scope reverted). Entry deleted from `~/go/gosmo/OPEN-THREADS.md`.

**Source:** `~/go/gosmo/OPEN-THREADS.md` § `ScriptDatabaseObjectList`: a user
mapped to a certificate or key.

**Bug:** with `IncludePermissions`, the principals block emits `CREATE USER …
FROM CERTIFICATE`/`ASYMMETRIC KEY`. The script never creates certificates or
keys, so replay into an empty database fails on that user, then on its role
memberships and grants.

**Fix:** extend the `grantScope` approach (`scripter_database_security.go`,
`buildDatabaseSecurityParts`). When a scope is set, write a
certificate- or key-mapped user as a comment that names the securable it
needs. Then comment out every statement that names that user: role
memberships, GRANT/DENY by or to it, and `ALTER AUTHORIZATION` to it. Follow
the existing `leftOut` comment style so all left-out items read the same.
A single-object `ScriptUser` is out of scope (no `grantScope`), so leave it
unchanged.

**Tests:** a unit test in `scripter_database_security_test.go` (a cert-mapped
user + membership + grant → all three commented, nothing else changed). Then
a live replay on 13 and 17: create a certificate, a user `FROM CERTIFICATE`,
a membership and a grant in a disposable database. Script it with
`ScriptDatabaseObjectList`, replay into an empty database, and expect no error.
Delete the open-threads entry.

### F2 — gossms: File > Open of an image file doesn't open a picture panel

**Done 2026-11-18.** `openQueryFile` sniffs the first `pictureSniffLen` bytes
after the `.sqlplan` branch; a match goes to `openPictureFile`, which opens a
`PicturePanel` titled with the base name, `filePath` set (Save writes back),
and no connect. New `NewPicturePanelBytes`/`decodePictureBytes` take raw
bytes; the hex path for result cells is unchanged. The file dialog has no
extension filter, so images are listed. Unit test
`TestOpenQueryFileSniffsPictures` (PNG, JPEG, a PNG named `.sql`, a script);
driven in tmux: Ctrl+O on a PNG and a JPEG opened picture panels, zoom and
Ctrl+W close worked, no query panel. README and F1 help name the new entry
point. Entry deleted from `docs/open-threads.md`.

**Source:** `docs/open-threads.md` § Picture viewer: what is left.

**Fix:** in `openQueryFile` (`internal/tui/app_panel_actions.go`), after the
`.sqlplan` branch, run `sniffPicture` on the file's first `pictureSniffLen`
bytes (`internal/tui/picture_panel.go`). On a match, open a picture panel
titled with the file's base name instead of a query panel, and don't connect
it. `NewPicturePanel` takes a hex string today. Add a constructor that takes
raw bytes, so the file isn't hex-encoded only to be decoded again. Keep the
hex one for result cells. Decide by content, never by extension, so a `.sql`
file that starts with PNG magic still gets sniffed. Check the file dialog's
filter still lets image files be picked.

**Tests:** a unit test that opens a PNG and a `.sql` file through the
`openQueryFile` callback path and asserts the panel type each time. Then drive
the binary in tmux: Ctrl+O on a PNG and a JPEG, zoom, close, and confirm no
query panel and no connect. Update `README.md` if it lists the picture
viewer's entry points. Delete the open-threads entry.

### F3 — gossms: Windows clipboard opened with a NULL owner

**Source:** `docs/open-threads.md` § Windows clipboard: what is left.

**Risk:** `OpenClipboard(0)` + `SetClipboardData` is documented to fail. It
never has on win10cli, and since 2026-11-18 an RDP client (Remmina) passes
too: 21 of 21 writes reached it, and paste works. A real clipboard manager
(Ditto) passes as well, with 450 round trips and 0 failures. Only the one
early hang is unexplained. This step is now **preventive and optional**: do
it only if a Windows user reports a failed or frozen copy, or to match the
documented contract. The fallback is already named: make a message-only
window the owner.

**Fix:** in `internal/tui/os_clipboard_windows.go`, create one message-only
window (`RegisterClassExW` + `CreateWindowExW` with `HWND_MESSAGE`). Because
the window belongs to its creating thread, and `withClipboard` locks an OS
thread per call, create the window per call on that locked thread and destroy
it after `CloseClipboard`. Then pass the window handle to `OpenClipboard`. Keep
the 1 s open timeout and the retry loop. Use `syscall.NewLazyDLL` only, with no
new dependency, so the no-CGO, no-build-tag rule holds.

**Tests:** `scripts/wintest.sh test ./internal/tui/ -run Clipboard`. Repeat
the 300-round-trip probe and the simulated-listener runs from the open-threads
entry. Check clipboard history (Win+V) records the writes. Rerun the RDP
check: connect Remmina to win10cli (its saved profile), then build a probe
test binary that calls `osClipboardWrite`/`osClipboardRead`. Run it inside the
RDP session through a `schtasks /create … /it /ru radu_` task, since ssh runs
outside that session, and compare against `xclip -o -selection clipboard`.
Repeat it with Ditto running: it is installed on win10cli and starts at
login. Space the writes at least 400 ms apart, since Ditto merges faster
changes, and count `Main` rows in `%APPDATA%\Ditto\Ditto.db`.

### F4 — gosmo + gossms: Fabric Warehouse detected from the hostname

**Source:** `docs/open-threads.md` § Environment (review 2026-11-18, E4).

**Bug:** `db.newServerConn` (`internal/db/connection.go`) sets `IsFabricDW`
from the `datawarehouse.fabric.microsoft.com` suffix and copies it into
gosmo's exported `Server.IsFabricDW` field. A private endpoint, a DNS alias or
any other gosmo caller gets SQL Server catalog queries.

**Fixable now (code):** move the decision into gosmo's `Connect`/`loadInfo`.
Detect on EngineEdition 11, use the hostname suffix only as a fallback, and
expose read-only `Server.IsFabricDW()` with a `ConnectionOptions` override
for tests. This is a breaking gosmo change: the field becomes a method, and a
tagged release must note it. In gossms, read it from the Server.
`ServerConn.IsFabricDW` becomes a method or goes, with about 25 mechanical
call sites. Follow the `dev-with-local-gosmo` skill.

**Needs live:** what tells Fabric from Synapse serverless, since both are
edition 11 (`DATABASEPROPERTYEX(DB_NAME(), 'Edition')`, `@@VERSION`). Until
the Fabric contributor probes it, keep the hostname as the tiebreak inside
gosmo. The API moves now and the detection gets better later. Keep a
shortened entry for the probe.

**Tests:** gosmo unit tests for the edition + hostname matrix and the
override. Run gossms `go test ./...` and `staticcheck`. Do a live smoke on 13
and 17 (must report false), plus `TestLiveVersionSweep` on 13.
