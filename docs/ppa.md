# Debian/Ubuntu packaging plan

How `apt-get install gossms` gets to work on Ubuntu and Debian-like distros.
`docs/homebrew.md` is the sibling document for macOS, and the two share a
deliberate design choice — **ship the binary the release already builds, do not
rebuild from source downstream**. The apt-repository route described here is
**built**; a Launchpad PPA is not, and § A real Launchpad PPA, later says why.

Read § Findings first. Two of them decide the whole approach, and both were
measured, not assumed.

## Findings

Measured on 2026-09-08, on Ubuntu 26.04.1 LTS with Go 1.27.1 and a real
`go1.26.0` toolchain downloaded for the purpose.

**1. Vendoring solves the `replace` directive completely.** `go mod vendor`
copies the sibling gosmo checkout into `vendor/`, recording
`# github.com/radix29/gosmo v0.0.11 => ../gosmo` in `vendor/modules.txt`. With
`../gosmo` then deleted outright and `GOPROXY=off`, `go build ./cmd/gossms`
still succeeds. So a source-built package is *not* blocked by the `replace`,
unlike a Homebrew source formula pulling a plain GitHub tarball. `vendor/` adds
23 MB to the source tarball.

**2. Ubuntu's Go is too old, and that is the blocker.** `go.mod` declares
`go 1.27` and `toolchain go1.27.1`. Launchpad builders have **no network
access**, so a builder cannot fetch a toolchain — it fails with
`toolchain not available`, which was reproduced locally. What the archive
actually ships (queried from the Launchpad API):

| Series | Version | `golang-defaults` | Newest packaged toolchain |
|---|---|---|---|
| noble | 24.04 LTS | Go 1.22 | none newer |
| plucky | 25.04 | Go 1.24 | none newer |
| questing | 25.10 | Go 1.24 | `golang-1.25` |
| resolute | 26.04 LTS | Go 1.26 | `golang-1.26` |

So **24.04 LTS — the largest installed base — cannot source-build gossms at
all**, and no series can build it while `go.mod` says 1.27.

**3. Neither codebase actually needs Go 1.27.** With the `go` directive lowered
to 1.26 in gossms *and* in the vendored gosmo, the real offline `go1.26.0`
toolchain builds `./cmd/gossms` cleanly. The 1.27 requirement is declarative in
both `go.mod` files, not a language or stdlib dependency. Note the second half:
the first attempt failed with
`github.com/radix29/gosmo in vendor/modules.txt requires go >= 1.27`, so a
source-built package would need **gosmo's** `go.mod` lowered too — a change in
the other repo, under `~/go/gosmo/CLAUDE.md`'s rules, for packaging's benefit
alone. Whether Go 1.25 (questing) also works was not tested.

**4. The binary has no dependencies.** Releases are `CGO_ENABLED=0` static, so
the `.deb` needs no `Depends:` beyond the implicit ones — no libc versioning
problem, and one `amd64` package works on every series from 24.04 up.

## The decision

**Chosen and built: a signed apt repository of prebuilt `.deb`s, published from
the release workflow.** Users get:

```sh
curl -fsSL https://radix29.github.io/apt/gossms.asc \
  | sudo tee /etc/apt/keyrings/gossms.asc > /dev/null
echo "deb [signed-by=/etc/apt/keyrings/gossms.asc] https://radix29.github.io/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/gossms.list
sudo apt-get update && sudo apt-get install gossms
```

It ships the exact binary that was built and tested, serves 24.04 LTS and
Debian and Mint alike, needs no toolchain gymnastics and no gosmo change, and
reuses the release pipeline the Homebrew job already established.

**Not recommended as the first step: a real Launchpad PPA.** The
`add-apt-repository ppa:radix29/gossms` one-liner is genuinely nicer, and
Launchpad does the arm64 build and hosting for free. But per findings 2 and 3
it costs: lowering the `go` directive in **both** repos, dropping 24.04 LTS
(or shipping a bootstrap toolchain), a 23 MB vendored orig tarball per upload,
a Launchpad account with a registered GPG key and signed Code of Conduct, and
a per-series upload each release. It stays worth doing later — § A real
Launchpad PPA, later sketches it — but it should not gate `apt-get install`.

## What was built

### The repository — https://radix29.github.io/apt

`radix29/apt`, public, served from `main` at the repository root through
GitHub Pages. `.nojekyll` is present, or Pages' Jekyll pass would skip the
directories apt needs — which also means the README is not rendered, so a hand-
written `index.html` carries the install instructions at the root. Both were
confirmed live (`/` and `/gossms.asc` return 200). `pool/`, `dists/` and `gossms.asc` are all generated by
the release workflow; only `README.md` and `.nojekyll` are written by hand.

Local checkout: `~/go/apt`.

### Two credentials, both scoped to that one repository

- **`APT_REPO_DEPLOY_KEY`** — an ed25519 deploy key with write access on
  `radix29/apt` (key id 162689226), private half stored as a secret on
  `radix29/gossms` and kept locally at `~/go/id` (`~/go/id.pub` alongside).
  Same pattern as the Homebrew tap, for the same reason: `GITHUB_TOKEN` cannot
  write to another repository.
- **`APT_REPO_GPG_KEY`** — a dedicated **RSA-4096** signing key, fingerprint
  `468B0CE5FFDEE82439741EC393F25CAB61497D93`, generated for this and nothing
  else. Its public half is published as `gossms.asc` in the apt repo root and
  is what users import into `/etc/apt/keyrings`.

  RSA rather than ed25519 deliberately: a key that users add to their trust
  store should be the boring choice that every `gpgv` in every derivative
  understands, not the modern one.

  **Losing this key is the expensive failure.** The GitHub secret cannot be
  read back, so if it is lost, a new key must be generated and every existing
  user has to import it by hand before `apt-get update` works again. The
  private half is kept at `~/go/secret.asc` and
  `~/.config/radix29-apt-signing-key.asc`; both are outside any git repository,
  and must stay that way.

### The `apt` job in `.github/workflows/release.yml`

Gated on `if: github.ref_type == 'tag'`, like the `homebrew` job. It:

1. Downloads `gossms_<tag>_linux_{amd64,arm64}.tar.gz` and **verifies each
   against the release's own `checksums.txt`** before unpacking. Packaging an
   unverified archive would launder a corrupted download into a signed
   repository, which is the one thing signing exists to prevent.
2. Builds a `.deb` per architecture: the binary into `/usr/bin/gossms`,
   `LICENSE` into `/usr/share/doc/gossms/copyright`, `Section: database`,
   `Priority: optional`, and **no `Depends`** — the release binaries are
   `CGO_ENABLED=0` static, confirmed with `file` on a real asset.
3. Regenerates `Packages` for both architectures with `dpkg-scanpackages`
   **from the whole pool**, then writes `Release` with a short Python step.
4. Signs `Release` into `InRelease` and `Release.gpg`, then **verifies its own
   signature with `gpgv`** against the published public key before pushing — so
   a broken signature fails the job rather than every user's next
   `apt-get update`.
5. Commits and pushes, only when something actually changed.

`dpkg-scanpackages` comes from `dpkg-dev` and `Release` is generated in Python,
so the job needs no `apt-utils` install on the runner.

Two details worth keeping:

- **Indices are rebuilt from the full pool, never appended to.** `Packages`
  lists every version apt may install; an index carrying only the newest entry
  silently makes older versions uninstallable and breaks
  `apt-get install gossms=0.0.9`.
- **Directory modes are set explicitly.** `dpkg-deb --root-owner-group` fixes
  ownership but not mode, and the runner's umask leaves directories
  group-writable (`0775`), which dpkg flags. `find -type d -exec chmod 0755`
  handles it — caught by inspecting a real built package, not by reading docs.

## What was verified, and how

No container runtime was available on this machine, so the client side was
driven with a sandboxed `apt` root instead — real `apt-get`, no root, no
containers:

- All three job scripts were extracted from the workflow YAML and **run
  locally against the real `v0.0.9` release assets**, producing valid `amd64`
  and `arm64` packages. This is what caught the directory-mode problem and
  proved the indented heredocs survive YAML extraction.
- `gpgv` reports `Good signature` on both `InRelease` and `Release.gpg`, using
  the same `gossms.asc` a user would import.
- The generated tree was served over HTTP and a real `apt-get update` accepted
  it **with no signature warning**; `apt-cache policy` resolved
  `Candidate: 0.0.9`, and `apt-get -d install gossms` downloaded the package.

Still unverified, and the reason the README change is held back:

- A genuine `dpkg -i` on a clean 24.04 / 26.04 / Debian container.
- `arm64` on real hardware or under qemu — the package builds, but nothing has
  executed its contents.
- `lintian`, which is not installed here.
- Extracting the `.deb` and running `gossms --version` exits 1 silently, which
  is **expected**: `v0.0.9` predates the flag, ignores its arguments, and dies
  trying to open a screen with no TTY, logging to the log file rather than
  stderr. The first release carrying the flag is the one to re-test.

## Steps left

1. Tag a release; confirm the `apt` job publishes and that Pages serves
   `dists/stable/InRelease`.
2. On a clean container per series: add the key and source, `apt-get update`,
   `apt-get install gossms`, `gossms --version`, then upgrade from the previous
   version. Run `lintian` on the `.deb` while there.
3. The README's **APT — Debian, Ubuntu and derivatives** subsection is already
   written, ahead of the first `.deb` existing — the same bet as the Homebrew
   one. It ships with the tag that first publishes packages; until that tag,
   `apt-get update` finds no `dists/`.

## A real Launchpad PPA, later

Worth adding on top once the apt repo works, purely for the
`add-apt-repository ppa:radix29/gossms` ergonomics. What it needs, in order:

1. A Launchpad account, the Ubuntu Code of Conduct signed, and a GPG key
   registered against it — uploads are rejected unsigned.
2. `go` lowered to 1.26 in `gossms/go.mod` **and** `gosmo/go.mod` (finding 3),
   or a build-dependency on a toolchain the target series actually has.
3. A `debian/` directory: `control` (`Build-Depends: debhelper-compat (= 13),
   golang-1.26-go`), `rules` running `dh` with `GOFLAGS=-mod=vendor` and
   `GO111MODULE=on`, `changelog` per series, `copyright` in DEP-5 form for
   GPL-3.0-or-later, and `source/format`.
4. `vendor/` committed into the orig tarball, since builders have no network.
5. `debuild -S -sa` then `dput ppa:radix29/gossms <changes>`, once per series,
   with a `~noble1`/`~resolute1` version suffix so upgrades order correctly.
6. arm64 builds enabled on the PPA (amd64 only by default).

Decide then whether the PPA supersedes the apt repo or runs alongside it.
Running both means two things to keep in step at every release.

## Open questions

1. **Which series to test against?** The packages are architecture- rather than
   series-specific, so this only sizes the container matrix in step 2.
2. **Debian too, or Ubuntu only?** Costs nothing extra with a static binary —
   only a line in the README and a container in the matrix.
3. **Is lowering the `go` directive to 1.26 in both repos acceptable in
   principle?** Not needed for what was built; it is the gate on the Launchpad
   PPA route ever happening.
4. **Pool growth.** Every release adds ~11 MB of binaries to `radix29/apt`'s
   git history, permanently. Fine for years; worth a pruning policy eventually,
   deciding how many old versions `Packages` should keep offering.
